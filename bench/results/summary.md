# 측정 결과 요약 (2026-10-11)

A = 기존 방식 (Tomcat + `@Async` chatTaskExecutor + RestTemplate + SseEmitter), `backend/`
B = WebFlux 분리 서비스 (Netty + WebClient + Flux SSE), `ai-chat/`

측정 환경: 로컬 단일 머신(M-series, Docker Desktop 8 CPU / 7.7GB). 앱 컨테이너는 각각 2 vCPU / 1.5GB 제한, JVM `-Xmx1g`.
외부 LLM 은 실측 지연(첫 토큰 700ms, 토큰 30개 10ms 간격, 쉐도잉 1300ms)으로 고정한 mock(`bench/mock-gpt`).
k6 는 컨테이너 밖(호스트)에서 실행. A 와 B 는 따로 측정. 실패율은 전 구간 0%.

## 1. 채팅 스트리밍 (동시 사용자 50→800, 각 60초)

손님(k6) 쪽 "첫 바이트까지" p95. mock 하한선은 700ms.

| 동시 사용자 | A p95 | A p99 | B p95 | B p99 |
|---|---|---|---|---|
| 50 | 7,331ms | 7,788ms | 707ms | 708ms |
| 100 | 16,216ms | 16,445ms | 707ms | 710ms |
| 200 | 14,035ms | 17,224ms | 708ms | 711ms |
| 400 | 10,390ms | 10,893ms | 712ms | 726ms |
| 800 | 2,234ms | 11,405ms | 791ms | 871ms |

전체 6분 합산 (`full2-*-chat-summary.txt`):

| | A | B |
|---|---|---|
| 메시지 첫 바이트 p95 / p99 | 10,875 / 13,026ms | 765 / 830ms |
| 메시지 전체 p95 | 11,199ms | 1,094ms |
| 처리한 대화 수 / 초 | 68.3 | 117.0 |
| 세션 생성(Redis 만) p95 | 828ms | 71ms |

서버 쪽 (Prometheus 5초 간격, `full-*-chat-per-stage.md`):

| | A | B |
|---|---|---|
| JVM 스레드 | 60 → 233 | 21 (변화 없음) |
| 톰캣 바쁜 스레드 | 800명 구간 200/200 | 해당 없음 |
| chatTaskExecutor | 활성 5 → 10, 큐 100/100 | 해당 없음 |
| OpenAI 동시 연결 | - | 최대 482 |
| 힙 최대 | 273MB | 106MB |
| CPU 최대 | 39% (423 req/s) | 85% (702 req/s) |

### 해석
- A 는 50명에서 이미 p95 7초, 100명에서 16초. 원인은 chatTaskExecutor 설정: core 5 / max 10 / queue 100. 자바 ThreadPoolExecutor 는 **큐가 꽉 차기 전에는 core 를 넘겨 스레드를 늘리지 않는다**. 즉 "최대 10개"로 설정돼 있어도 큐 100개가 찰 때까지는 5개로만 돈다. 메시지 1건이 1초 이상 스레드를 잡으니 초당 5건이 상한이고 나머지는 큐에서 기다린다.
- 200명부터 큐가 차면 CallerRunsPolicy 로 톰캣 스레드가 직접 GPT 를 기다린다. 병렬이 늘어 줄은 짧아지지만(800명 p95 2.2초) 톰캣 스레드 200개가 전부 묶이고, p99 는 11초로 남으며, GPT 와 무관한 세션 생성까지 p95 828ms 로 밀린다. 서버 쪽 지표는 톰캣이 요청을 집어든 뒤부터만 재므로 800명 구간의 접속 대기열 대기는 서버 지표에 안 보인다. 그래서 구간 비교는 k6 숫자를 쓴다.
- B 는 800명까지 스레드 21개 고정, p95 는 mock 하한 700ms 에 거의 붙어 있다. 800명에서 CPU 85% 에 닿으며 p95 가 791ms 로 오른 것은 2 vCPU 한계. 같은 시간에 A 보다 1.7배 많은 요청을 처리한 결과다.
- "WebFlux 가 WebClient/가상 스레드보다 빠르다"는 주장은 이 측정으로 할 수 없다. 비교한 것은 blocking 구조 vs non-blocking 구조다.

## 2. 쉐도잉 전환 (동시 사용자 10→100, 각 60초)

한 번의 전환 = 대화 메시지 4개(사용자 2 + 봇 2)를 각각 GPT 로 변환. mock 하한선 1,300ms.

| | A | B |
|---|---|---|
| 쉐도잉 p50 / p95 / p99 | 13,475 / 16,303 / 17,136ms | 1,304 / 1,310 / 1,320ms |
| 메시지 첫 바이트 p95 (같은 시간대) | 14,547ms | 708ms |
| 전환 처리 수 / 초 | 1.26 | 7.66 |
| 4분 동안 완료한 전환 | 349 | 1,980 |

### 해석
- A 는 쉐도잉 문장 생성도 같은 chatTaskExecutor 에 작업을 던진다(기존 TranslateService 패턴). 채팅 메시지와 쉐도잉 변환이 5개 스레드를 나눠 쓰니 서로 줄을 세우고, 10명만 동시에 눌러도 10초 넘게 걸린다.
- B 는 flatMapSequential(동시성 4)로 4문장을 병렬 호출해 mock 하한 1.3초에 붙는다. 100명 동시 전환에서도 변화 없음.
